AMD AI DevMaster Hackathon Track 2 · Private AI Agents

GatherPoint.AI

A local-first group meetup planning agent that finds the geographically fairest and semantically best spot — running end-to-end on AMD Radeon GPU + ROCm.

The Challenge

01Group planning is geometrically unfair — a naive midpoint ignores who can actually get there.
02Real constraints are semantic: vegan diets, budgets, biking vs. transit, availability.
03Generic assistants hallucinate venues instead of verifying reachability and requirements.

The Solution — Four Pillars

01 · REASONINGReAct Agent on Local vLLM

LangChain ReAct loop over a quantized Llama-3-8B-Instruct served locally on the Radeon GPU. Decomposes requests, plans multi-step, self-corrects on malformed tool calls (max_iterations=6), and bails out gracefully on impossible requests.

02 · DATAGIS Toolchain & Isochrone Intersection

Per-person, per-mode travel isochrones → common reachable region → POI search with exact polygon filtering → fairness ranking by travel time, rating, and review count.

03 · COMPUTECustom HIP C++ Kernel

Bare-metal intersect.hip: shared-memory block reduction + atomic center accumulation, bridged zero-copy via ctypes into a FastAPI microservice — the Radeon GPU as a true compute engine.

04 · MEMORYLocal RAG & Preference Memory

ChromaDB + all-MiniLM-L6-v2 embeddings computed on ROCm. POST /retrieve_profiles injects saved profiles & preferences into every planning prompt — across sessions.

How It Works — Split Deployment

LOCALStreamlit UI + Agent Orchestrator + GIS data gathering (Google Maps APIs for tool data only)
RADEON CLOUDvLLM (:8001) — quantized LLM · FastAPI (:8000) — RAG retrieval & GPU center calculation
BRIDGESSH port-forwarding (8000/8001) keeps the local agent talking to the GPU node
FLOWUser request → memory & profile retrieval → ReAct tool call → isochrone intersection on GPU → ranked venues → final answer with per-person travel rationale
